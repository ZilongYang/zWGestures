## 1. 目标与已核实的问题

### 已用数值复现的三个问题（不是猜测）

用你 `~/Library/Application Support/zWGestures/config.json` 的真实定义（`Close = [-50,50,-50,0,0,0]`，
即屏幕上的「下 50 → 右 50」）复算当前识别器：

| 你画的东西（屏幕坐标） | 期望 | 当前度量实测 |
|---|---|---|
| 下 467 → 右 210（V:H = 2.2，就是你的截图） | 关闭 | 到 `Close` = **0.109 > 阈值 0.10 → 不识别** |
| 下 → 右（V:H = 0.5，横比竖长 2 倍） | 关闭 | 到 `Enter` = **0.086，到 `Minimize` = 0.085**，两条都过阈值 → 列表靠前的 **Enter 胜出** |
| 下 100 → 右 H → 下 100（Enter 的三段形状），H = 200 | Enter | 到 `Enter` = **0.120 > 0.10 → 不识别**（H = 300 时 0.19，更差） |

根因：`StrokeNormalizer.normalize` 把**整条笔画按总弧长缩放到 1** 再逐点比欧氏距离
（`StrokeNormalizer.swift:16-25`），于是「每一段占全长的比例」被当成了形状本身。后果有两个：
比例一变就漏识别；某一段特别长时其余段的方向信息被淹没，方向完全不同的三条手势
（Enter / Minimize / Fullscreen）距离挤到 0.085~0.12 之间，胜负由列表顺序决定。
顺带发现同一件事的另一面：**L 形画到 2.2:1 时，它到「粘贴」（一条直线）的距离只有 0.075，
比到自家 `Close` 还近**。

### 你确认的第 3 条：松手后动作执行「偶尔慢半拍」

代码里查到的具体回归（`a65d89b` 性能硬化引入，不是键盘掩码那条）：

- 改之前 `InputCoordinator.updateRecognition` 只在主线程存一份 context（几乎零成本）；
- 改之后它**在主线程构建整份 `RecognitionIndex`**（每个目标 × 每条手势的归一化 + 触发解析）；
- 而 `AppDirectory` 每 3 秒（以及每次切换/启动/退出应用）刷新一次并回调 `onChange`
  → `EngineController.pushRecognitionContext()` → 走上面那条贵路径。

也就是说：**tap 线程确实变快了，但「松手→主线程执行命令」这条路上每 3 秒多了一段主线程忙活**，
正好卡在你松手那一瞬间时就是「慢半拍」。「偶尔」也吻合（约 3 秒一次的窗口 + 应用切换时）。

**不打算回退的**：键盘掩码（`EventTapMask`，冻机根因）、超时主动停用（`EventTapHealthPolicy`）、
索引预计算本身。这些只有好处或属于安全防线；只修「被误放在热路径上的那部分」。

## 2. 成功判定（可机检）

1. 截图那条 L（V:H 2.2，带起笔漂移）→ 命中 `关闭`；V:H 从 0.4 到 4.0 全部命中 `关闭`。
2. 同样的 L **不再**命中 `Enter` / `Minimize` / `Fullscreen` / `Paste` / `Web 搜索`。
3. `下→右→下` 三段，中间那段长度 0.4×~3× 竖段 → 一律命中 `Enter`；`上→右→下` 一律 `Fullscreen`；
   `下→右→上` 一律 `Minimize`（现在 H≥2× 就漏）。
4. 现有行为零变化（测试守着）：闭环手势「细长环命中 / 正圆不命中」的容差、`拷贝/剪切` 靠左键区分、
   同形按列表顺序、禁用不参与、应用手势集继承。
5. 主线程不再因 `AppDirectory` 刷新而构建索引：一轮实机手势中「识别完成 → 命令开始执行」
   超过 50 ms 的次数为 0（新增读数可直接看）。
6. `make test` 全绿（含新增的形状结构测试与手绘失真回归），`make lint` 通过。

## 3. 改动方案

### 3.1 新的形状结构距离（新文件 `ZWGCore/Sources/ZWGCore/Recog/StrokeStructure.swift`）

- `StrokeStructure.make(from points:)`：滑动平均平滑（窗口 5，端点不动）→ Ramer–Douglas–Peucker
  简化，容差 = `max(8, 0.09 × 外接矩形对角线)` → 反复合并夹角 < 25° 的相邻段 →
  丢弃长度占比 < 4% 的段。产出 `[Segment{direction: CGVector, lengthFraction: CGFloat}]`。
- `StrokeStructure.distance(live, stored)`：段序列上的对齐（小规模 DTW，n,m ≤ 8）：
  - 匹配代价 = `0.75 × 方向差(弧度/90°，封顶 1) + 0.25 × |长度占比差|`
  - 增删段代价 = `1.0`（**这是关键**：2 段的 L 对 3 段的 Enter 因此被判 ~0.33，不再靠列表顺序兜底）
  - 归一化 `… / max(n, m)`，结果落在 0…1。
- **已知取舍**：方向差按 90° 线性打分，所以 ±30° 的手抖几乎不罚、90° 反向直接满分。

### 3.2 两类手势走两套度量（保住闭环手势的既有容差）

在构建索引时给每条存储手势定 `kind`：

- **`.loop`**：存储折线的**起点与终点距离 ≤ 10% 总弧长**（即「画出去再原路返回」）→
  你配置里是 `Web 搜索` / `退格` / `删除` / `Terminal` / `Activity Monitor`。这类**沿用现有弧长距离
  + 0.10 阈值**，所以 `loopShapeToleranceMatchesTheDesign`（细长环+椭圆的容差）与「正圆不命中」的
  行为**逐字不变**。
- **`.structure`**：其余全部（Close / Enter / Minimize / Fullscreen / Reload / 四段自由形状…）→
  新的结构距离 + 新阈值 `structureThreshold`。

**选取规则完全不动**：仍然是 `modifierCount` 多者优先 → 列表靠前优先 → 距离兜底
（`GestureRecognizer.bestCandidate`）。你之前要求的「按排序优先」不受影响，因为同形手势的结构距离
本来就相等。

### 3.3 阈值与设置

- `RecognitionSettings` 增 `structureThreshold`（初值 0.15，实现时用 3.6 的手绘失真回归 +
  `ConfusionReportTests` 标定；`matchThreshold` 保持 0.10 供 `.loop` 用）与 `simplifyToleranceFraction`。
- `RecognitionMatch` 增 `metric: .structure | .arcLength`，调试面板据此显示 `距离 0.047(形状)`。

### 3.4 索引与设置界面的一致性

- `PreparedGesture` 增 `kind`，构建时算好结构签名（主线程一次）；`.structure` 的手势不再保留
  32 点归一化形状 → tap 线程更省。
- `WGStrokeConflict`（设置界面的冲突检测）改用与引擎同一套「kind + 距离 + 阈值」，
  否则界面报的冲突和引擎实际行为会对不上；`WGStrokeConflictTests` 的不变量测试保留。
- `WGStrokeRecorder.simpleForm` 的往返校验（现在用弧长距离 ≤ 0.06）改成结构距离 ≤ 0.10：
  否则**你手画一条 2.2:1 的「下→右」新手势时，会被判成「不像简单形状」，悄悄存成自由形状**
  （同一个 bug 的录制侧表现）。`WGStrokeRecorderTests` 的「录一个向上笔画必须等价于原版 Copy」
  等断言保留。

### 3.5 修「松手后偶尔慢半拍」

1. **拆分更新路径**（`InputCoordinator`）：
   - `applyConfig(_ config: WGConfig, targetMode:)`：构建索引（配置变化时才调用）；
   - `updateTargeting(applications:focusedPID:)`：只换 context（每 3 秒/切换应用的路径），
     复用已构建的 `RecognitionIndex`；
   - 用 `WGConfig: Equatable` 做「配置没变就不重建」的兜底比较；缓存逻辑抽成 ZWGCore 里的
     可测小类型 `RecognitionIndexCache`（带构建计数，便于单测断言「目录变化不重建」）。
2. **索引构建移出主线程**：在专用串行队列 / `Task.detached(priority: .utility)` 构建
   `RecognitionIndex`（`Sendable`），完成后在主 actor 换引用。配置真变了也不会卡住松手路径。
3. **`EngineController`**：`appDirectory.onChange` 只调 `updateTargeting`；
   `apply(config:targetMode:)` 才调 `applyConfig`。
4. **tap 停用策略按类型区分**：把判定抽进 `EventTapHealthPolicy.action(for:)` →
   `tapDisabledByUserInput` **立刻重新启用**（恢复冻结前的逻辑，它不是「回调慢」的信号）；
   `tapDisabledByTimeout` 保留 0.5 s 退避与「60 秒内 3 次就放弃」。`EventTapSafetyTests` 增两条断言。
5. **可观测**：调试面板增 `idx rebuilds` / `last handoff ms` 两行；`handleCompletedGesture`
   到 `CommandExecutor.execute` 之间超过 50 ms 记一条 warning 日志。这样「是否真的修好」有据可查，
   而不是凭感觉。

### 3.6 测试

- 新增 `StrokeStructureTests.swift`：平滑/RDP/合并的边界（直线、圆角、抖动直线、闭环、极扁 L）、
  段数不等的对齐代价、方向反转必须满分。
- 新增「手绘失真回归」（`GestureRecognizerTests` 内新 suite）：夹具里每条手势生成 20 个失真样本
  （每段长度 ×0.35~2.5、方向 ±12°、2.5 px 抖动），断言**目标手势必须过阈值**；
  对同形重复组只断言组内有人过。**先跑这个再定 `structureThreshold`**。
- 你报的两个用例固化成具名测试（截图那条 L、三段长横的 Enter、以及「L 不得命中 Enter/Minimize/Paste」）。
- 现有 `GestureRecognizerTests` 里那批硬编码距离断言按新度量重新标定（保留「同形状 < 0.01」
  「细长环命中/正圆不命中」「闭环互相区分」「尺度无关」这些语义断言）；`ConfusionReportTests`
  改为经引擎同一入口取距离；`RecognitionPerformanceTests` 增加索引构建耗时的上界。
- 「目录变化不重建索引」在 ZWGCore 层用 `RecognitionIndexCache` 单测（App target 进不了 `swift test`）。

## 4. 边界与已知不做

- **不修**你四个自由形状手势（`重新载入` / `其他窗口` / `下一应用` / `上一个应用`）之间的互相混淆：
  它们的形状本来就是同一种「∧」，现有度量下两两距离 0.022~0.068，今天就已经由列表顺序裁决。
  新度量不会让它更糟，但也不会治好 —— 这点会写进 ROADMAP 并当面说明，若要治只能靠改形状或加修饰键。
- `Terminal` / `Activity Monitor` 是原版自带的**退化重复定义**（零宽竖向折返），无法可靠区分，保持现状。
- 不做滚动/边角触发、不做服务端/UI 大改。
- 每次 `make test` 前先 `make lint`；改完由你在实机上验收两条：① 画截图那种 L；
  ② 连画十几个手势确认没有「慢半拍」。

## 5. 假设

- 你同意「同形手势按列表顺序、其余按形状」仍是正确语义（本次不改选取规则）。
- 你同意闭环手势（Web 搜索/退格/删除）继续用旧度量 —— 这是为了不牺牲你已经在用的「细长环」容差。
- 第 3 条的根因（主线程索引重建）是本次**主要嫌疑**，但要用 3.5.5 的读数在一轮实机上确认；
  若读数显示另有元凶，按读数再修，不硬套结论。

## 实施结果：与计划的差异（2026-10-06 实施后补记，本节不属于原方案）

**六条成功判定全部达成**（数据见 [`ROADMAP.md`](ROADMAP.md) 第 21 节）：
截图那条 L 0.109 → **0.063**；竖横比 0.4~4.0 全部命中「关闭」；三段 Enter 的中间横 0.4×~3×
全部命中；闭环手势行为未变；`idx rebuilds` 启动后停在 1、交接毫秒数为个位数；
`make lint` 通过 + **284 项测试全绿**。

四处**偏离方案**（都是实测推翻了方案里的判断，逐条记下原因）：

1. **方向权重从 0.75 提到 0.85**（方案 §3.1 写的是 0.75/0.25）。0.75 时竖横比 8:1 的 L 到自家定义
   是 0.153（正好压线），提到 0.85 后是 0.122，同时「真正不同的形状最近一对」仍有 0.283 的余量。
2. **加了两个方案里没有的保护**：分析点数封顶 48（不封顶时成本随笔画点数线性增长，800 点比 50 点
   慢 5.3 倍）；点数太少时跳过滑动平均（对 2~4 顶点的存储定义做均值会把拐角平均成直线，
   「关闭」对自家定义一度变成 0.252）。
3. **DTW 加了三种短路**（单段闭式解、段数相同时取对角、段数不同才走小规模 DP 且用栈上临时分配）。
   方案只写了「小规模 DTW」，照做的话每条候选一次堆分配，热路径反而从 403 µs 涨到 1256 µs。
4. **录制器保持弧长校验，把方案 §3.4 那条改回去了**。方案说「录制器也改用结构距离，否则
   2.2:1 的 L 会存成自由形状」；实测发现结构度量会把**真正的圆弧**也看成「两段折线」，
   于是曲线会被掰成直角（`curvedStrokesStayFreehand` 正是钉这个的）。取回退：宁可让比例极端的
   L 存成自由形状（**只是不好看，识别两种都正常**），也不把曲线掰直。

两件**方案外多做的事**：

- `updateTargeting` 加了「已发布的索引必须属于这份配置，否则退回真重建」的守卫，并把启动顺序
  改成「先交规则集、再启动应用目录」——否则启动时会先白白构建一份「0 条手势」的索引，
  而且「配置变更的构建还在队列里」时会把过期索引发布出去（表现为手势静默不响应）。
- `RecognitionPerformanceTests` 的计时改成「多批取最小」：Swift Testing 并行跑测试会让单批均值
  上下翻倍，那才是这几条守卫以前看起来 flaky 的原因。

一条**方案里写错、实施时被数据纠正**的既有记录：方案 §3.2 沿用了「非重复形状不会同时通过阈值」
这条理由（原写在 ROADMAP 第 12 节）。实测旧度量下 `Enter` 与 `Close` 只差 **0.100**，
这条理由是错的，已在 ROADMAP 第 12 节更正 —— 现在「列表靠前优先」之所以安全，
靠的是新度量把不同形状拉开到 0.283，而不是阈值。
